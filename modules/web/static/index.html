Help

CLUTCH Operating Protocol

CLUTCH is a local-first operating layer for Codex sessions, projects, PCs, repositories, backups, snapshots, and multi-PC collaboration. This Help page is not a feature list. It explains the order of operations, what to ask the active Codex session to do, and which actions require explicit operator approval.

CLUTCH is built for AI and robotics labs where compute resources, large models or datasets, hardware-adjacent approval boundaries, and multi-PC work often overlap.

Why CLUTCH

Core Differentiators

Multi-PC Codex Collab

CLUTCH does more than manage one local Codex session. It binds Codex sessions across multiple PCs by project, role, and machine-local path. Main, worker, observer, heartbeat, task, acknowledgement, result, and file handoff evidence are kept in the same project context.

Visible Collab Monitor

Collaboration should be visible while it is happening. The monitor shows whether the worker is fresh, which project task it is looking at, and whether transport roles agree with CLUTCH project bindings.

Large Project Snapshots

Large model weights, datasets, robot bags, media, and checkpoints should not be forced into git. CLUTCH keeps source heads, paths, URIs, hashes, artifact pointers, and validation commands together so a project can be restored.

Away Development

Away work is bounded work, not open-ended automation. A plan records the objective, allowed scope, stop conditions, verification, and expiry. Work outside the plan must stop and ask.

Web UI and Notifications

The Web UI turns raw CLUTCH state into operator-readable status. Notifications bring the operator back when long work needs attention. Routine work should still be issued as natural language to the active Codex session.

Research Lab Ready

CLUTCH is aimed at research groups that split work across several workstations, keep large artifacts outside git, and need a clear boundary around hardware-adjacent work.

First run

First Install and Web Startup

The public first-run wizard creates local settings for this PC only: machine id, project workspace root, artifact store, GitHub setup preference, collab preference, admin guard, and Web console preference. It ships with no preset accounts, IP addresses, SSH aliases, tokens, or lab paths.

  1. Run the first-run wizard once to create this PC's local CLUTCH setup.
  2. Start each new Codex session with `session-entry`. When enabled, this starts the Web console backend.
  3. Local desktop sessions may open a browser safely. SSH or headless sessions should print the URL instead.
  4. GitHub sync uses your own account and remotes only after you configure them.
  5. Collab setup can guide wired-LAN, SSH, Codex exec, or shared-folder transports, but peer addresses and credentials stay local.
  6. After first setup, the dashboard and Help should explain the next action instead of repeatedly asking setup questions.
Operating protocol

Operating Protocol

Start by checking which project and role this Codex session is attached to. Then read the Dashboard and Monitor. Normal development instructions should go to the active Codex session in natural language, not to a growing set of Web buttons.

  1. Run `session-entry` to inspect project matching, re-entry docs, sync state, and attach guidance.
  2. When role matters, attach explicitly with `session-attach --project ... --bind-role main|worker|observer`.
  3. Use Sessions to verify active bindings. For projects with `machine_role_policy=none`, active binding is the role source.
  4. Read Dashboard warnings as review evidence, not automatic failures. Dirty work, publish gates, and stale history mean different things.
  5. Attention items separate inspection from action. `safe_to_run_without_approval=True` means the suggested check is read-only. `approval_required=True` means the actual fix, apply, publish, restore, or lifecycle action still needs approval.
  6. Ask the current Codex session for routine work, complex edits, worker delegation, or away-development planning.
  7. Default commands stay intentionally small: status, refresh preview, preview-only sync/collab checks, monitor status, and recovery evidence.
  8. Before risky edits, handoff, or release, check local backups, snapshots, metadata, validation evidence, and artifact pointers.
  9. Long-term context may live in `PROJECT_HISTORY.md`, git, snapshot metadata, backups, away logs, and durable project docs. The active checkpoint is not the only history.
  10. During collab, the main and worker machines should both have an operator-visible monitor.
  11. Restore, online publication, sudo, service, network, kernel, udev, credential, destructive restore, and hardware actions require explicit approval.
Command protocol

Command Principles

Codex Session First

Give real development instructions to the active Codex session in natural language. The session should read the binding, away plan, checkpoint, and approval boundary before choosing CLI commands.

Default Commands Stay Small

Default buttons are limited to checks that are worth repeating: status, preview, monitor, and backup evidence. Too many buttons make the console harder to validate and make approval boundaries easier to misunderstand.

Advanced Commands Are Evidence

Advanced commands are low-frequency evidence checks: lifecycle, snapshot metadata, artifact pointers, onboarding, and release validation. Apply and publish paths still require approval through the Codex session.

Web Buttons Are Not Delegation

Web buttons run registered CLUTCH CLI or API checks and show evidence. A button does not send arbitrary natural language work to another PC or command a worker session. Ask the active Codex session to delegate.

Read the console

Reading The Console

Dashboard

Start here for project and machine status. A warning is evidence that needs review, not always a failure. For example, dirty work may be recoverable while still blocking clean publication.

Attention Boundary

Attention items show an operator summary, suggested command, safe-to-run state, and approval-required state. Read-only checks can run immediately. Sync, apply, publish, restore, and lifecycle changes need approval.

Sessions

Read project roles by PC: main, worker, and observer. Expired or released bindings are history, not current authority.

Monitor

The visible collab monitor shows whether main and worker monitors are present, whether heartbeat is fresh, and which project owns recent task, ack, and result records. Stale task history from another project is useful context, not active selected-project work.

Projects

Inspect repo sync, versioning readiness, backups, away plan, data handling, and online policy for the selected project. CLUTCH binding is the project role source; transport role is runtime diagnostic state.

Backups

Compare local backups, local manifests, promoted metadata refs, and restore readiness. Recovery readiness and clean release validation are related but different judgements.

Machines

Inspect install state, reconnect state, runtime, online identity, worker link, target source, and repo alignment for this PC. Lifecycle readiness is not robot safety certification.

Collab

Collab Standard

CLUTCH collab uses active project bindings on each PC as the main and worker role source. Collab transport carries tasks, heartbeat, and evidence. Transport role does not replace the CLUTCH project binding.

  1. The main session keeps project direction, approval boundary, and checkpoint context.
  2. The worker performs bounded work in its own machine-local workspace.
  3. The monitor should show local role, peer role, CLUTCH binding, transport role, target source, task, acknowledgement, result, and heartbeat.
  4. If role mismatch or binding-role-only state appears, ask the Codex session to interpret the role state before delegating.
  5. Complex delegation should be requested in natural language through the active Codex session, not through a generic Web button.
Data and release

Data, Backups, and Release

Project Data Policy

Data policy is project-specific. A small project may fit entirely in git and local backups. Model or training work usually keeps code and configs in git while checkpoints, datasets, raw logs, and Hugging Face caches stay in local or external artifact storage with paths, URIs, or hashes.

Backup / Snapshot

A backup is a local recovery bundle. A snapshot is reproducibility metadata for a point in time. Before release, code head, dirty state, validation command, and artifact pointers should explain the same state.

Online Publish

Online git is the approved code source of truth when a project configures it. Publish authority still depends on project policy and the publisher machine. Dirty work can block clean publication readiness.

New PC Onboarding

New PC onboarding starts with `machine-collab-guide`. Repeatable onboarding should be tied to a release tag, release manifest, bootstrap path, machine registration review, and onboarding checklist.

Natural language

Common Requests

These prompts are safe starting points to paste into the active Codex session. The Web console shows state and evidence; the operator still gives development instructions and approval decisions in natural language.

Enter A New Session

Example prompt

I opened a new Codex session. Check the CLUTCH entry state.

Expected result

`session-entry` reports project match, re-entry docs, attach guidance, notification mode, and sync state.

Pick A Project Role

Example prompt

Attach this session to my-project as main and show the start docs I should read first.

Expected result

`session-attach` creates the active binding and the Sessions view shows the main role and re-entry document order.

Summarize Status

Example prompt

Summarize the current project status and attention items in plain language.

Expected result

`project-status`, `overview`, and attention plans summarize repos, bindings, backups, next actions, safe-to-run state, and approval-required state.

Create A First Project

Example prompt

Register this git folder as a CLUTCH project and confirm CLUTCH metadata stays outside the project repo.

Expected result

`project-create` records the machine-local workspace while keeping project source and local CLUTCH state clearly separated.

Dry-Run Readiness

Example prompt

Check whether this PC can continue the project, including git sync and snapshot metadata, without writing changes.

Expected result

`project-refresh --dry-run` previews repo sync, versioning, restore readiness, and artifact pointer state without changing the workspace.

Back Up Before Risk

Example prompt

Create a local project backup before this refactor and explain what files and repo bundles were captured.

Expected result

`project-backup` records backup id, repo bundle, copied docs, missing optional files, and restore location.

Snapshot Reproducibility

Example prompt

Snapshot the current state and tell me which commit and artifact pointers would be needed to restore it later.

Expected result

`project-snapshot --write` records source head, dirty state, validation command, artifact pointers, and restore plan in a manifest.

Inspect Artifact Boundaries

Example prompt

Identify datasets, model weights, logs, and caches that should stay out of git and be recorded as artifact pointers.

Expected result

CLUTCH reviews data policy and artifact pointer state, then separates source-controlled files from external storage records.

Check The Collab Monitor

Example prompt

Check whether both main and worker collab monitors are visible.

Expected result

`collab-monitor-status` separates visible/running state, CLUTCH binding, transport role, and task history.

Confirm Worker Roles

Example prompt

Before I delegate work, confirm the CLUTCH binding and collab transport roles agree.

Expected result

The Monitor view separates role source, binding role, transport role, target source, peer freshness, and delegation risk.

Delegate A Narrow Task

Example prompt

Ask the worker machine to inspect only training logs and report memory bottlenecks and failed runs. Do not edit files.

Expected result

The main session states approval boundaries and scope, then worker task, ack, and result evidence remain visible.

Prepare Away Work

Example prompt

Create an away-development plan for documentation and test hardening only. Do not publish, delete, or touch hardware.

Expected result

The away plan records objective, allowed scope, forbidden actions, stop conditions, verification, checkpoints, and expiry.

Report Away Progress

Example prompt

Report what changed under the current away plan, which checks passed, and where you must stop.

Expected result

`project-away-report` summarizes progress, scope compliance, validation results, and remaining stop conditions.

Prepare GitHub Sync

Example prompt

Show the remote and GitHub setup I need for online sync using my own account, without storing secrets in CLUTCH.

Expected result

CLUTCH explains remotes, branches, account state, and sync policy while keeping tokens and private keys outside CLUTCH metadata.

Onboard A New PC

Example prompt

Show a dry-run plan for adding a new worker PC, including bootstrap, shared folder, collab setup, and monitor checks.

Expected result

`machine-collab-guide` outlines install, machine id, shared transport, role attach, and monitor validation before applying changes.

Troubleshoot Web Startup

Example prompt

If the Web console does not open or my project is missing, narrow the cause in the safest order.

Expected result

`web-console-status`, `clutch_doctor`, `session-entry`, project registry, and local settings are checked read-only first.

Verify A Local Install

Example prompt

Before I rely on this install, run the local checks that prove Help, Monitor, backups, and command registry readiness.

Expected result

The Web smoke, doctor, and verification matrix checks confirm the local install is ready for first use.

Safety

Approval and Safety Boundary

CLUTCH state, worker replies, and monitor heartbeat do not authorize robot motion, hardware recovery, sudo, network, kernel, udev, service changes, credential handling, destructive restore, or online publication. CLUTCH's job is to expose the right project, machine, session, path, backup, runbook, and approval boundary.

도움말

CLUTCH 운영 프로토콜

CLUTCH는 Codex 세션, 프로젝트, PC, 저장소, 백업, 스냅샷, multi-PC 협업을 한 곳에서 다시 진입하고 확인하게 해주는 local-first 운영 계층입니다. 이 도움말은 버튼 설명서가 아니라 어떤 순서로 확인하고, 어떤 일은 활성 Codex 세션에 자연어로 맡기며, 어떤 일은 명시적 운영자 승인이 필요한지 알려주는 운영 기준입니다.

CLUTCH는 여러 워크스테이션, 큰 모델과 데이터셋, 하드웨어 근처 승인 경계, 장시간 작업이 겹치는 AI 및 로보틱스 연구실 환경을 기준으로 설계되었습니다.

왜 CLUTCH인가

핵심 차별점

Multi-PC Codex 협업

CLUTCH는 하나의 Codex 세션만 관리하지 않습니다. 프로젝트, 역할, machine-local 경로를 기준으로 main, worker, observer 세션을 묶고 task, ack, result, heartbeat, 파일 handoff 근거를 같은 프로젝트 맥락에 보관합니다.

보이는 협업 모니터

Monitor 탭은 worker가 fresh한지, 어떤 프로젝트 task를 보고 있는지, transport role과 CLUTCH project binding이 일치하는지 보여줍니다.

큰 프로젝트 복구 근거

모델 weight, dataset, robot bag, media, checkpoint를 git에 강제로 넣지 않습니다. CLUTCH는 source head, 경로, URI, hash, artifact pointer, 검증 명령을 함께 기록해 복구 판단을 돕습니다.

Away Development

자리비움 작업은 무제한 자동화가 아닙니다. 목표, 허용 범위, 중단 조건, 검증, 만료 시각을 기록하고 범위를 벗어나면 멈추고 물어봐야 합니다.

Web UI와 알림

Web UI는 raw CLUTCH 상태를 운영자가 읽을 수 있는 상태로 바꿉니다. 알림은 장시간 작업이 다시 주의를 요구할 때 운영자를 불러오지만, 승인 자체를 대신하지는 않습니다.

연구실 환경 기준

여러 PC에 일을 나누고, 큰 artifact는 git 밖에 두며, 하드웨어 근처 작업에는 선명한 승인 경계가 필요한 연구 그룹을 기준으로 설계되었습니다.

첫 실행

설치와 Web 시작

공개 배포판의 first-run wizard는 이 PC의 로컬 설정만 만듭니다: machine id, 프로젝트 workspace root, artifact store, GitHub 설정 방식, collab 선호도, admin guard, Web console 선호도입니다. 사전 설정된 계정, IP 주소, SSH alias, token, 연구실 경로는 포함하지 않습니다.

  1. first-run wizard를 한 번 실행해 이 PC의 CLUTCH 로컬 설정을 만듭니다.
  2. 새 Codex 세션은 `session-entry`로 시작합니다. 설정되어 있으면 Web console backend도 함께 시작됩니다.
  3. 로컬 desktop 세션은 브라우저를 열 수 있고, SSH/headless 세션은 URL을 출력해야 합니다.
  4. GitHub 동기화는 사용자가 직접 계정과 remote를 설정한 뒤에만 사용됩니다.
  5. collab 설정은 wired LAN, SSH, Codex exec, shared folder를 안내할 수 있지만 peer 주소와 자격 증명은 로컬에 남습니다.
  6. 첫 설정 뒤에는 Dashboard와 Help가 다음 행동을 설명해야 하며 같은 설정 질문을 반복하지 않아야 합니다.
운영 순서

Operating Protocol

먼저 이 Codex 세션이 어떤 프로젝트와 역할에 attach되어 있는지 확인합니다. 그 다음 Dashboard와 Monitor를 읽고, 실제 개발 지시는 Web 버튼을 늘리는 대신 활성 Codex 세션에 자연어로 줍니다.

  1. `session-entry`로 프로젝트 매칭, re-entry 문서, sync 상태, attach 안내를 확인합니다.
  2. 역할이 중요하면 `session-attach --project ... --bind-role main|worker|observer`로 명시적으로 attach합니다.
  3. Sessions 탭에서 active binding을 확인합니다. `machine_role_policy=none`인 프로젝트는 active binding이 역할 기준입니다.
  4. Dashboard warning은 자동 실패가 아니라 review evidence입니다. dirty work, publish gate, stale history는 서로 다른 의미입니다.
  5. `safe_to_run_without_approval=True`는 read-only 점검을 뜻하고, `approval_required=True`는 apply, publish, restore, lifecycle 변경에 승인이 필요하다는 뜻입니다.
  6. routine work, 복잡한 수정, worker 위임, away-development 계획은 현재 Codex 세션에 자연어로 요청합니다.
  7. 위험한 수정, handoff, release 전에는 backup, snapshot, metadata, validation evidence, artifact pointer를 확인합니다.
  8. restore, online publication, sudo, service, network, kernel, udev, credential, destructive restore, hardware action은 명시적 승인이 필요합니다.
버튼과 명령

Command Principles

Codex 세션이 우선

실제 개발 지시는 활성 Codex 세션에 자연어로 줍니다. 세션은 binding, away plan, checkpoint, approval boundary를 읽은 뒤 필요한 CLI 명령을 선택합니다.

기본 명령은 작게

기본 버튼은 status, preview, monitor, backup evidence 같이 반복해서 확인할 가치가 있는 read-only 중심 작업으로 제한합니다.

고급 명령은 근거

lifecycle, snapshot metadata, artifact pointer, onboarding, release validation 같은 고급 명령은 저빈도 evidence check입니다. apply와 publish는 Codex 세션을 통한 승인이 필요합니다.

Web 버튼은 위임이 아님

Web 버튼은 등록된 CLUTCH CLI 또는 API check를 실행하고 근거를 보여줍니다. 임의의 자연어 작업을 다른 PC나 worker 세션에 보내는 기능이 아닙니다.

콘솔 읽기

Reading The Console

Dashboard

프로젝트와 머신 상태를 처음 보는 곳입니다. warning은 검토가 필요한 근거이며 항상 실패를 뜻하지는 않습니다.

Sessions

프로젝트별 PC 역할을 main, worker, observer 기준으로 확인합니다. 만료되거나 released된 binding은 현재 권한이 아닙니다.

Monitor

main과 worker monitor가 보이는지, heartbeat가 fresh한지, 최근 task/ack/result가 어떤 프로젝트에 속하는지 확인합니다.

Projects

선택 프로젝트의 repo sync, versioning readiness, backup, away plan, data handling, online policy를 확인합니다.

Backups

local backup, manifest, promoted metadata ref, restore readiness를 비교합니다. 복구 준비와 clean release validation은 다른 판단입니다.

Machines

이 PC의 install, reconnect, runtime, online identity, worker link, target source, repo alignment를 확인합니다.

Collab

Collab Standard

CLUTCH collab의 역할 기준은 각 PC의 active project binding입니다. collab transport는 task, heartbeat, evidence를 운반하는 구현 계층이며, transport role이 CLUTCH project binding을 대체하지 않습니다.

  1. main 세션은 프로젝트 방향, approval boundary, checkpoint context를 유지합니다.
  2. worker는 자기 machine-local workspace에서 제한된 작업을 수행합니다.
  3. Monitor는 local role, peer role, CLUTCH binding, transport role, target source, task, ack, result, heartbeat를 보여줘야 합니다.
  4. role mismatch나 binding-role-only 상태가 보이면 위임 전에 Codex 세션에 역할 상태 해석을 요청합니다.
데이터와 공개

Data, Backups, and Release

Project Data Policy

데이터 정책은 프로젝트별입니다. 작은 프로젝트는 git과 local backup으로 충분할 수 있지만, 모델/학습 작업은 checkpoint, dataset, raw log, cache를 artifact pointer로 기록하는 편이 안전합니다.

Backup / Snapshot

backup은 로컬 복구 bundle이고 snapshot은 특정 시점의 재현성 metadata입니다. release 전에는 code head, dirty state, validation command, artifact pointer가 같은 상태를 설명해야 합니다.

Online Publish

online git은 프로젝트가 설정한 경우 승인된 code source of truth가 됩니다. publish 권한은 project policy와 publisher machine 기준을 따릅니다.

New PC Onboarding

새 PC는 `machine-collab-guide`로 시작합니다. 반복 가능한 onboarding은 release tag, manifest, bootstrap path, registration review와 연결되어야 합니다.

기대 결과

안전

Approval and Safety Boundary

CLUTCH 상태, worker 응답, monitor heartbeat는 robot motion, hardware recovery, sudo, network, kernel, udev, service change, credential handling, destructive restore, online publication을 승인하지 않습니다. CLUTCH의 역할은 올바른 프로젝트, 머신, 세션, 경로, 백업, runbook, approval boundary를 보이게 하는 것입니다.
